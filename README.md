# HiveGrid

HiveGrid is a multi-agent energy system simulation for a housing society. Home agents schedule household loads around resident preferences and available energy. A Society agent coordinates prices and fairness, while a Grid agent sends tariff, stress, and response-cap signals. Homes can trade surplus rooftop solar peer to peer. The goal is to reduce energy waste and peak demand while respecting resident constraints.

## How it works

- **Home agents** schedule AC, EV charging, geysers, laundry, and home batteries for 50–100 synthetic flats.
- **The Society agent** receives society loads and comfort deficits, then adjusts price multipliers and fairness weights.
- **The Grid agent** supplies time-of-use prices, capacity limits, and stress signals. In learned mode, its model head proposes these signals within programmed bounds.
- **The peer-to-peer market** matches home solar offers with household bids using a midpoint price.
- The simulation runs for 96 steps, each representing 15 minutes. Weather uses an offline local cache of historical PVGIS data for Nagpur when present; otherwise the simulator logs a warning and uses its synthetic fallback. The checked-in cache covers 2023.

## Input provenance

- **Real historical weather:** hourly PVGIS/ERA5 2 m temperature and plane-of-array irradiance for Nagpur (21.15 N, 79.09 E), converted from UTC to IST and cached locally. The simulator does not need internet access at runtime.
- **Modeled solar:** PVGIS's modeled 1 kWp AC output is multiplied by each synthetic home's configured kWp and a 0.9 derate. This is modeled generation, not measured household solar output.
- **Tariff structure:** `tariff/msedcl_tariff.json` is a configurable simulation structure. Its solar-hours window is 09:00–17:00 as requested. Rupee values and tariff percentages remain marked placeholders because the society's applicable category and rates must be supplied. Until rupee rates are filled in, monetary dispatch and P2P trading are disabled. P2P clearing stays within the configured feed-in/grid-price band.
- **Synthetic inputs:** household loads, appliance profiles, preferences, and household meter-like values are generated by seeded simulation code. HiveGrid contains no real household consumption dataset.

The overview dashboard and `GET /data/provenance` identify which inputs are historical, modeled, synthetic, or awaiting tariff configuration. Residents can submit structured preference requests in the portal; supported constraints take effect after a society administrator approves and applies them.

## Run the demo on Windows

Use Python 3.12 or later and Node.js 18 or later. In PowerShell, from the project folder:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
npm --prefix frontend ci
npm --prefix frontend run build
python -m uvicorn api.main:app --reload
```

Open [http://127.0.0.1:8000/](http://127.0.0.1:8000/) for the React dashboard. Start the learned-agent simulation from the overview or Simulation Studio; the dashboard advances the actual Python simulator and reads its homes, metrics, time series, and agent events. API documentation is at [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs).

The simulator reads `data/real/pvgis_nagpur_2023.csv` if present and never fetches data on startup. To fetch another historical year explicitly and list cached heatwave demo dates:

```powershell
python data/fetch_weather.py --year 2023
python data/list_heatwave_days.py --year 2023
```

For the current cache, the hottest day at or above 43 °C is 2023-05-14 (PVGIS hourly Tmax 43.19 °C). Select it with `demo_date` and `weather_year` in the `POST /simulation/start` JSON body, for example `{"n_homes":56,"seed":7,"policy":"learned","scenario":"summer","demo_date":"2023-05-14","weather_year":2023}`.

For frontend-only development, start the backend on port 8000, then run `npm --prefix frontend run dev`. Vite proxies simulator API requests to `http://127.0.0.1:8000`; override this with `HIVEGRID_API_TARGET` if needed.

The integrated dashboard shows current society demand, solar generation, grid import, learned-agent status, simulation time series, and backend-emitted agent events. The Home Agents page reads profiles and schedules from the active simulation. These are simulated values, not live energy readings. Admin and resident request pages use backend records; login, invitations, and other portal views remain demo-only.

## Resident request approval

Requests are stored in SQLite at `data/hivegrid_requests.sqlite3` and persist across backend restarts. Approval applies supported constraints to the selected home in the active simulation: temperature setpoint/window, EV deadline/charge target, and minimum battery reserve. The home's safety checks reject infeasible constraints. A successful approval is recorded as **Applied** and queued for the next simulation interval. Requests can still contain unsupported flexible-appliance or free-text preferences; the review page identifies those so an approval does not imply they were enforced. Applying a request requires a running simulation. Resetting the simulation clears active overrides and returns applied requests to review.

This portal is a local prototype without real authentication or access control. Do not expose its request endpoints to the public internet or use it to control physical equipment.

## Learned agents

`HivePolicy` is a shared four-layer, 144-wide transformer with separate HOME, SOCIETY, and GRID output heads. In learned mode, all three heads are active:

- The HOME head proposes household schedules. Actions pass through the feasibility shield, and the teacher schedule supplies EV charging protection and fallback.
- The SOCIETY head proposes a price multiplier and household fairness weights. Programmed bounds limit its proposals.
- The GRID head proposes price, stress, and response-cap signals. Grid safety rules bound the price and cap, and real grid stress signals cannot be suppressed.

The heads are trained by imitation: a rule-based teacher generates input/action examples, and the neural network learns to reproduce those actions. This is not training on real utility or household data.

The committed checkpoint at [`artifacts/hive_policy.pt`](artifacts/hive_policy.pt) was initialized from random weights and trained for four epochs on 5,000 seeded examples. It is a demonstration checkpoint trained on synthetic teacher examples; retrain it with the date-separated commands below before reporting date-held-out results. On a separate 512-example synthetic seed, its previously measured held-out mean squared error was:

| Head | MSE |
| --- | ---: |
| HOME | 0.00793 |
| SOCIETY | 0.00249 |
| GRID | 0.00973 |

A [readable preview of three complete training examples](teacher_dataset_preview.json) includes each example's 48-step observation sequence and role-specific target action. Regenerate a date-separated dataset with the demo date reserved for test (by default, collection chooses the hottest cached day at or above 43 °C):

```powershell
python collect.py --samples 5000 --seed 11 --year 2023 --demo-date 2023-05-14 --output data/teacher.pt
python train.py --data data/teacher.pt --epochs 12 --output artifacts/hive_policy.pt
python eval.py --model artifacts/hive_policy.pt
```

To collect a larger dataset and train a new checkpoint from scratch:

```powershell
python collect.py --samples 100000 --seed 11 --year 2023 --demo-date 2023-05-14 --output data/teacher.pt
python train.py --data data/teacher.pt --epochs 12 --output artifacts/hive_policy.pt
python eval.py --model artifacts/hive_policy.pt
```

`collect.py` partitions calendar dates into disjoint training, validation, and test groups, and asserts the demo date appears only in test. Training uses train indices and validation for reporting; test samples are not used for gradient updates. Collection and training support `--smoke` for a small pipeline check. Generated training datasets are ignored by Git.

## Verification and limits

P2P solar matching is simulated and enabled with explicitly labeled tariff assumptions in `tariff/msedcl_tariff.json` (₹10/kWh grid base, ₹2/kWh feed-in, plus assumed time-of-day factors). These are demo placeholders, not verified MSEDCL rates. The dashboard provenance badge and `/metrics` report `ASSUMED`; trades are logged as Society Agent events and counted in metrics. Replace the assumptions with the applicable tariff before using them for any real cost estimate.

Previously reported results from a seeded 50-home heatwave run were zero EV deadline, temperature comfort, or energy-balance violations, 8.84% peak reduction, and 0.962 Jain comfort. Those figures were measured with the earlier synthetic-weather scenario; they are not a result for the current PVGIS-backed scenario and do not show real-world performance or broad generalization.

To run the simulator's checks and terminal smoke demo:

```powershell
pytest
python demo_run.py --smoke
```

Battery, EV, and thermal dynamics are simplified. The learned heads imitate the synthetic teacher and have not been validated against real homes or grid operations. Society and Grid retain programmed bounds and fallbacks for safety.
